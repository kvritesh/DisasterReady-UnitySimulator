# DisasterReady — AI Continuation Guide

Read this if you are an AI agent (Claude, GPT, or otherwise) picking up this project with zero prior conversation history. It is written to be self-sufficient. A companion file, `DISASTERREADY_HANDOFF.md`, has more exhaustive detail (full script table, exact inspector values, per-prop-category editing instructions) — read this file first for orientation, then that one for specifics. `DISASTERREADY_ENVIRONMENT_INVENTORY.md` has a per-asset/prefab inventory if you need to know exactly what's placed where.

## What this project actually is

A Unity vertical-slice prototype called "DisasterReady": a small 3D mountain-valley town the player explores in third person, completing three preparedness missions, then experiencing a scripted (not AI-driven, not real-data-driven) "emergency" they must escape by reaching high ground. It ends in a "preparedness score" screen. It is explicitly, repeatedly documented in its own code comments as a scripted demo — do not add or imply real predictive/AI/hazard-data capability that isn't there; if you're asked to "make it smarter," push back and clarify what's actually wanted, because the existing code's honesty about being a scripted heuristic is a deliberate design choice, not a placeholder to be papered over.

## The one thing you must understand before touching anything

**The active scene, `Assets/Scenes/DisasterReady_AizawlValley.unity`, is entirely generated by code.** The generator is `Assets/Scripts/Editor/AizawlValleySceneBuilder.cs` (static class, `[InitializeOnLoad]`), invoked via the Unity Editor menu **`DisasterReady > Build Aizawl Valley Scene (Dedicated)`**. Running it:
1. Calls `EditorSceneManager.NewScene(NewSceneSetup.EmptyScene, NewSceneMode.Single)` — this **deletes everything currently in the open scene**, no merge, no warning.
2. Rebuilds the entire hierarchy (terrain tiles, ramps, roads, buildings, POIs, player, camera, UI, missions, emergency system) from scratch via C# calls in that one file.
3. Saves over `DisasterReady_AizawlValley.unity` and re-registers it as Build Settings index 0.

There is also an auto-build hook (`[InitializeOnLoadMethod] OnInit`) that runs this once automatically the first time the Editor domain loads in a session — but it explicitly refuses to run while Play Mode is active, entering, or exiting (`EditorApplication.isPlayingOrWillChangePlaymode` guard; this was itself a bug fixed in git history: "Fix: Play Mode always wins over AizawlValleySceneBuilder auto-build hook" — do not regress that fix).

**Practical implication: if you're asked to change anything about the environment (move a building, add a tree, adjust a road, fix a collider), the correct fix is almost always an edit inside `AizawlValleySceneBuilder.cs`, not a Hierarchy/Inspector edit in the Unity Editor.** A Hierarchy edit will be silently wiped the next time anyone (including the auto-build hook) reruns the builder. The only exception is a true one-off/throwaway change nobody expects to survive a rebuild.

There is a second, older scene-building system — `Assets/Scripts/Editor/SceneBuilder.cs` (menu `DisasterReady/Build Demo Scene`) builds `Assets/Scenes/DisasterReadyDemo.unity`, which uses a real Unity `Terrain` + heightmap (`TerrainGenerator`/`ProceduralTerrainDataProvider`) instead of the flat-tile-terrace approach. It is NOT the current focus (it's Build Settings index 1, not 0) — don't confuse the two systems. If someone asks about "the terrain height/slope system," they may mean this other, currently-unused-in-practice system; check which scene is actually meant before editing.

## Current scene & gameplay (verified, not assumed)

Player spawns at world `(0, 0.52, -32)` on "Level 0" of a four-tier terraced valley (levels at world Y ≈ 0.46 / 2.96 / 5.96 / 8.96, connected by ramps at Z≈-14, Z≈15, Z≈41.5). Camera-relative third-person movement (WASD/arrows, Space=jump, Shift=sprint; right/left mouse-drag orbits camera, scroll zooms). Three POIs (hospital west, shelter east, summit north/high) each a 7m-radius trigger sphere. Missions must complete in the fixed order they're listed in code (`find_highest`, `find_shelter`, `find_hospital`) regardless of which POI the player physically reaches first — see `MissionManager.NotifyZoneEntered`'s `if (current.Id != missionId) return;` gate. Completing all three fires a scripted emergency (atmosphere shift, siren, "safe direction" arrow heuristic) that resolves when the player reaches the summit's second trigger (`EmergencyObjectiveTrigger`), showing a final score screen. Full script-by-script reference and exact numbers are in `DISASTERREADY_HANDOFF.md` Sections D-F.

## What NOT to change without a strong reason

- Don't touch the CharacterController's `center (0, 0.95, 0)` / `height 1.9` / `radius 0.45`, or `PlayerController`'s core movement math, without a specific, understood reason — this is tuned and currently working.
- Don't move the KayKit character's `Animator` component off the top-level instantiated GameObject onto `Rig_Medium` — see the long comment in `KayKitIntegration.SetupAnimator` explaining why that silently breaks all animation (path-binding mismatch between the FBX's baked curves and where Unity looks for them). This is a genuinely non-obvious Unity FBX-import gotcha, not arbitrary caution.
- Don't remove the `EditorApplication.isPlayingOrWillChangePlaymode` guard in `AizawlValleySceneBuilder.OnInit`/`OnPlayModeChanged` — it fixes a real prior bug where the auto-build hook would fight with Play Mode.
- Don't add real network calls, real geographic/DEM data fetching, or ML/AI-based prediction and then describe it as "the same demo, just better" — that would misrepresent what the project claims to be. If genuinely upgrading it that way is the goal, that's a real scope conversation to have explicitly, not something to slip in.
- Don't `git add -A` or `git add .` — there is a stray, untracked `_to_delete/` folder in the repo root full of leftover git-lock-file debris from this session's environment quirks (see below). Always `git add` specific, named files.

## How to modify environment / missions / gameplay

**Environment:** edit `AizawlValleySceneBuilder.cs`, using the existing helper functions (`PlaceBuilding`, `PlaceRoadStraight`/`PlaceRoadTile`, `CreatePoiMarker`, `CreateSignpost`, etc. — all documented with exact signatures in `DISASTERREADY_HANDOFF.md` Section G/H). Then run `DisasterReady > Build Aizawl Valley Scene (Dedicated)` from the Unity menu bar and save (Ctrl+S / Cmd+S).

**Missions:** add a `MissionDefinition` to the list built in `AizawlValleySceneBuilder.IntegrateGameplay`, and a physical trigger (`CreatePoiMarker` + `.MissionId`, or a bare `MissionZoneTrigger`) whose `MissionId` matches. See `DISASTERREADY_HANDOFF.md` Section F for the exact recipe.

**Gameplay systems:** `MissionManager`, `EmergencyScenarioController`, `PlayerController`, etc. are plain runtime `MonoBehaviour`s in `Assets/Scripts/` — edit them like normal Unity scripts. They get wired together by `AizawlValleySceneBuilder.IntegrateGameplay` at scene-generation time (public fields assigned there), so if you add a new public field that needs a scene reference, you must also assign it there — this project has no scene-persisted prefab variants doing that wiring for you.

## How to test

1. Open the project in Unity 6000.5.10f1 (or whatever version `ProjectSettings/ProjectVersion.txt` says at the time you're reading this — check it, don't assume it hasn't changed).
2. If you changed `AizawlValleySceneBuilder.cs`: run `DisasterReady > Build Aizawl Valley Scene (Dedicated)`, wait for it to finish (Console will log a `[AizawlValleySceneBuilder] SUCCESS!` line), then save the scene.
3. Check the Console: expect 0 errors. A handful of `CS0618` obsolete-API warnings in `DisasterReadyTransplanter.cs` are pre-existing and harmless.
4. Enter Play Mode, click "ENTER AIZAWL, MIZORAM", and actually play through: move with WASD, verify camera orbit (mouse drag) and zoom (scroll), walk into each POI, verify the HUD mission panel updates, verify the emergency sequence triggers after the third mission, verify the safe-direction arrow appears and points somewhere reasonable, walk to the summit, verify the result panel appears with a score.
5. For a specific stuck-movement bug: watch the Player GameObject's Transform Position/Rotation in the Inspector live while holding a movement key. See the diagnostic guidance in the "unfinished work" section above and in `DISASTERREADY_HANDOFF.md` Section J.
6. Don't claim something works from reading the code alone if you had the ability to actually press Play and check — this project's history includes multiple bugs that looked fine in code review but failed live (the ramp collider issues were exactly this kind of bug).

## How to commit (and a real environment quirk to know about)

Standard git: `git add <specific files>`, `git commit -m "..."`, `git push origin main`. Remote is `https://github.com/kvritesh/DisasterReady-UnitySimulator.git`, single branch `main`. **Never force-push, never squash or delete existing commits/tags, never `reset --hard`** — there is no other backup of this project's history.

If you're operating through a sandboxed/remote-shell environment (rather than a human sitting at the actual machine) and git commands hang for 1-2 minutes or fail with `fatal: Unable to create '.../.git/index.lock': File exists` even though nothing else is touching the repo: this specific machine/mount rejects plain file deletion (`unlink()`) inside `.git` with "Operation not permitted," but `mv`/`rename()` works fine. The fix is to `mv` the stale `.git/index.lock` (or `.git/HEAD.lock`) out of the `.git` directory immediately before retrying the git command. This is an artifact of the sandboxed automation environment, not a property of the repository — a human working directly on the machine won't encounter it.
