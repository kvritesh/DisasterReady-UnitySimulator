# DisasterReady — Handoff Document

Written at final Claude session handoff (2026-09-07). This is a practical reference, not a polished spec — paths, names and values below were read directly from the project on this date. If you change the project, re-verify anything load-bearing rather than trusting this file blindly.

## A. Project Overview

DisasterReady is a Unity vertical-slice prototype of a disaster-preparedness simulator/game. The player explores a small mountain valley town ("Aizawl Valley", modeled loosely on Aizawl, Mizoram), completes three preparedness missions (find the highest point, find the emergency shelter, find the hospital), then a scripted ("simulated, not AI-predicted") emergency triggers, and the player must reach higher ground to finish the demo and see a preparedness score.

**This is a scripted demo, not a real disaster-prediction system.** The code is explicit and repeated about this in comments — the emergency trigger is deterministic (fires the instant all missions are done), the "safe direction" arrow is a simple heuristic (elevation gain + alignment to the known objective, no ML, no real hazard data), and the preparedness score is a fixed formula, not a statistical model. Keep it that way — don't let future work quietly imply real prediction/AI capability that doesn't exist.

## C. Scene Structure

### Scenes in Build Settings (`ProjectSettings/EditorBuildSettings.asset`), in order:
1. **`Assets/Scenes/DisasterReady_AizawlValley.unity`** — index 0 (loads first in a build). **This is the active, playable prototype.** Entirely generated by an Editor script (see below) — do not hand-edit scene contents you expect to survive a rebuild; edit the generator script instead.
2. `Assets/Scenes/DisasterReadyDemo.unity` — an older/parallel scene built by a different Editor tool (`Assets/Scripts/Editor/SceneBuilder.cs`, menu `DisasterReady/Build Demo Scene`). Uses a real Unity `Terrain` component + heightmap (`TerrainGenerator`/`ProceduralTerrainDataProvider`), unlike the Aizawl Valley scene. Not the current focus; left alone this session.
3. `Assets/Scenes/SampleScene.unity` — default empty Unity template scene. Not used.

### How `DisasterReady_AizawlValley.unity` is built

It is **fully procedurally generated** by `Assets/Scripts/Editor/AizawlValleySceneBuilder.cs` (a static `[InitializeOnLoad]` Editor class, 2139 lines). Menu: **`DisasterReady > Build Aizawl Valley Scene (Dedicated)`**. Running this menu item:
1. Wipes the currently open scene (`EditorSceneManager.NewScene(EmptyScene, Single)`) — it does NOT merge into whatever is open.
2. Builds the entire hierarchy below from scratch via code (ground tiles, ramps, roads, buildings, POIs, player, camera, UI, missions, emergency system).
3. Saves to `Assets/Scenes/DisasterReady_AizawlValley.unity` and registers it as Build Settings index 0.
4. Takes a few inspection screenshots (see `CaptureInspectionScreenshots`, writes to a hardcoded path under `ScreenshotsDir` in the script — that path is a personal machine path from earlier development and will silently no-op if it doesn't exist; harmless).

**Consequence you must understand:** any edit you make by hand in the Scene view/Hierarchy (moving a building, adding a prop by dragging it into the Hierarchy) will be **silently discarded** the next time anyone runs `Build Aizawl Valley Scene (Dedicated)` — and there is also an auto-build hook (`OnInit`/`[InitializeOnLoadMethod]`) that runs this once automatically on a fresh Editor load if it hasn't run yet this session (it does NOT run automatically on every domain reload, and it explicitly never fires during Play Mode — see the `OnPlayModeChanged`/`isPlayingOrWillChangePlaymode` guard, git history: "Fix: Play Mode always wins over AizawlValleySceneBuilder auto-build hook"). **All lasting environment edits belong in `AizawlValleySceneBuilder.cs`, not in the Hierarchy.** Section G covers this in practice.

## E. Gameplay Flow (actual)

1. Scene loads -> `GameBootstrapper.Start()` disables `Player.ControlsEnabled` and `OrbitCamera.ControlsEnabled`, hides the HUD, shows the title screen.
2. Player clicks "ENTER AIZAWL, MIZORAM" -> `TitleScreenController.OnEnterPressed` -> `GameBootstrapper.HandleEnterPressed` hides title, shows HUD, enables player + camera controls.
3. `MissionManager.Start()` (already ran at scene load, before the title screen was even dismissed) fired the very first `OnMissionStarted`/`OnXpChanged` for mission 1 ("Find the Highest Point"); `HUDController.OnEnable` explicitly re-pulls this state so the HUD shows it correctly once revealed.
4. Player free-roams (camera-relative WASD/arrow keys + Space to jump + Shift to sprint; mouse drag to orbit camera, scroll to zoom) and walks into each POI's trigger sphere (7m radius) in any order — but only the *current* mission's zone actually completes anything; entering a later POI early is a no-op.
5. Each completion: `MissionManager` marks it complete, adds XP, fires `OnMissionCompleted` (banner shows "MISSION COMPLETE") and `OnMissionStarted` for the next mission (or `OnAllMissionsComplete` after the third).
6. `OnAllMissionsComplete` -> `EmergencyScenarioController.TriggerEmergency()`: HUD switches to "EMERGENCY OBJECTIVE", banner shows the "SIMULATED EMERGENCY — DEMONSTRATION ONLY" alert, atmosphere darkens/tints over ~2.2s, siren plays, `SafeDirectionGuide` activates (arrow appears above player), camera eases back.
7. Player follows the arrow (or just remembers where the summit is) to the summit POI, which also carries `EmergencyObjectiveTrigger`.
8. Reaching it -> `NotifyObjectiveReached()` -> `ResolveEmergency()`: guide/siren stop, atmosphere restores (~1.5s), player is frozen (`ControlsEnabled=false`), `PreparednessResultPanel` fades in showing score/missions/XP and a disclaimer that this is a scripted simulation. `WebGLBridge.SendResult(...)` fires (no-op outside WebGL).
9. That result panel is the end of the demo — nothing resets it; a fresh playthrough requires reloading the scene.

## F. Mission System

Three missions, defined inline in `AizawlValleySceneBuilder.IntegrateGameplay` (NOT in a ScriptableObject or JSON — they're hardcoded `MissionDefinition` objects):

```csharp
new MissionDefinition("find_highest", "Find the Highest Point", "Climb to the summit safe zone above the valley.", 100),
new MissionDefinition("find_shelter", "Locate the Emergency Shelter", "Find the fortified emergency community shelter.", 100),
new MissionDefinition("find_hospital", "Locate the Hospital", "Locate the emergency medical facility in the valley.", 100),
```

Order in the list is completion order — `find_highest` is listed first but its physical POI (the summit) is the farthest away, so in practice players usually reach hospital/shelter first physically but those don't register until `find_highest` (order 0) completes, since `MissionManager.NotifyZoneEntered` ignores any id that isn't `CurrentMission.Id`. **This is worth confirming is actually the intended design** — if you want a "reach whichever POI you find first" experience instead of a strict order, you'd need to remove the `if (current.Id != missionId) return;` gate in `MissionManager.NotifyZoneEntered` and instead look up any not-yet-complete mission whose id matches. Not changed this session (no evidence it's broken, just worth flagging as a possibly-unintended constraint).

### How to add a new mission

1. In `AizawlValleySceneBuilder.IntegrateGameplay`, add a new `new MissionDefinition("your_id", "Title", "Description", xpReward)` to the `missionManager.Missions` list, in the order you want it required.
2. Create (or reuse) a physical trigger for it. Two options:
   - If it's a POI-style destination: call `CreatePoiMarker(poiRoot.transform, "POI_YourThing", worldPos, PoiType.SomeType, "LABEL TEXT", color)` and set `.MissionId = "your_id"` on the returned `MissionZoneTrigger`. You may need to add a new value to `PoiType` enum (`Assets/Scripts/POI/PoiType.cs`) if none of `Hospital/EmergencyShelter/Summit` fit — it's cosmetic only (used nowhere except as a plain label field on `PoiMarker`, no switch statement depends on it, so adding a value is risk-free).
   - If it's not POI-shaped: create any GameObject with a `Collider` set to `isTrigger`, `AddComponent<MissionZoneTrigger>()`, set `.MissionId` and (if the default `"Player"` doesn't apply) `.PlayerTag`.
3. Re-run `DisasterReady > Build Aizawl Valley Scene (Dedicated)`.
4. `MaxXp` and the HUD's XP display update automatically (`MissionManager.Start()` sums `XpReward` over the whole list).
5. If your mission should also gate something else (like the emergency), you don't need to touch `EmergencyScenarioController` — it already subscribes to `OnAllMissionsComplete` regardless of list length or content.

## G. Environment Editing Guide

**Golden rule: everything in the Aizawl Valley scene is generated by `AizawlValleySceneBuilder.cs`. Edit the script, then re-run the menu command. Do not hand-edit the `.unity` scene file directly if you expect the change to survive.** (The one thing that *is* safe to hand-edit and will persist: anything outside this generation path, e.g. if you manually add a brand-new standalone GameObject after building and then save without ever running the builder again — but the instant someone reruns the builder, that hand-added object is gone, since `BuildScene()` calls `NewScene(EmptyScene, ...)` first.)

### Adding a building
Use the existing `PlaceBuilding(prefab, parent, name, pos, rotation, scale)` helper (defined ~line 1204) inside whichever section function makes sense (e.g. `BuildResidentialSettlement`, or add a new section function and call it from `BuildScene()`). Example, to add a house at Level 1:
```csharp
var newHousePrefab = AssetDatabase.LoadAssetAtPath<GameObject>($"{KayKitCityDir}/building_A.fbx");
PlaceBuilding(newHousePrefab, buildingsFolder, "House_L1_New", new Vector3(-6f, 3.0f, -3f), Quaternion.Euler(0f, 80f, 0f), Vector3.one * 2.2f);
```
Notes:
- `PlaceBuilding` always attaches a **generic `BoxCollider(4,4,4)` centered `(0,2,0)`** regardless of the prefab's real size/scale. For a building close to a walkway (like the Level 2 houses this session), this generic collider can be badly wrong for the building's actual footprint after scaling/rotation — verify clearance manually (or call `EnsureBoxCollider(go, customSize, customCenter)` yourself after `PlaceBuilding` returns, if you make it return the GameObject the way `PlaceRoadStraight` was changed to this session).
- Available house prefabs: `SyntyHousePrefab` (`SM_PolygonApocalypse_Bld_House_01`), and KayKit `building_A/B/C/D/E/F/G/H.fbx` under `KayKitCityDir` (`Assets/KayKit/CityBuilder/Assets/fbx (unity)`).
- Ground surface Y per level (see Section C table): L0=0.46, L1=2.96 (buildings sit slightly higher, ~2.99-3.0, matching road height), L2=5.96 (buildings at 5.5-6.0).

### Removing a building/prop
Delete or comment out its `Place...(...)` call in the script, then rebuild.

### Moving/rotating/scaling a prop
Edit the `Vector3 pos` / `Quaternion rot` / `Vector3 scale` arguments of its `Place...` call, then rebuild. All coordinates in this file are literal world-space meters (no relative/local offsets except within a single composite function like `BuildHospitalComplex`, which computes some child positions as `centerPos + offset`).

### Adding vegetation
See `BuildVegetationAndRocks` (~line 1238). Tree prefabs available: `SyntyTree01-04Prefab`, `SyntyTreeDeadPrefab`. Rock prefabs: `SyntyRock01-05Prefab`. Follow the existing pattern of `PrefabUtility.InstantiatePrefab` + name + position + `EnsureMeshCollider`/`StripColliders` + `SetStaticFlags`.

### Adding/modifying roads
`BuildRoadNetwork` (~line 660) uses `PlaceRoadStraight(fbxPath, parent, name, pos, yaw, pitch=0)` for straight segments (looped over a Z or X range in 2.0-unit steps to tile them) and `PlaceRoadTile(fbxPath, parent, name, pos, rotation)` for junctions/curves. Road FBX files live under `KayKitCityDir`: `road_straight.fbx`, `road_corner_curved.fbx`, `road_junction.fbx`. Every road tile gets a small flush `BoxCollider(2.0, 0.15, 2.0)` centered `(0, 0.05, 0)` automatically. **If you add road anywhere a `SlopedRouteRamp` invisible collider also passes through, strip the road tile's collider with `StripColliders(tile)`** (see the `z >= 35.5f` example at the end of the Level 2 loop) — overlapping colliders at slightly different heights is the exact bug pattern that caused this session's route-blocker debugging (see Section J).

### Modifying terrain (levels/terraces)
There is no heightmap terrain in this scene — "terrain" is flat `PlaceFlatGround` tiles stacked at fixed Y values per level, connected by ramps. To change a level's height, you must update: (a) every `PlaceFlatGround` call at that level, (b) the berm (`GameObject.CreatePrimitive(PrimitiveType.Cube)`, named `TerraceBerm_*`) above/below it, (c) the retaining-rock loop's Y and Z, (d) both adjacent `SlopedRouteRamp` calls' `bottomY`/`topY`, and (e) the visible ramp prefab's `position`/`localScale`. This is fiddly by hand — see `BuildTerracedValley` (~line 255) for the exact existing pattern per level, and match it.

### Adding a mission-relevant environment object
See Section F above — use `CreatePoiMarker` for a destination-style objective, or a bare trigger + `MissionZoneTrigger`/`EmergencyObjectiveTrigger` for anything else.

### Lighting/camera
`SetupLighting(envRoot.transform)` (~line 223) sets up the directional light/sky. `IntegrateGameplay` (~line 1353) configures the one and only camera (`OrbitCameraController` fields — FOV 55, near/far clip 0.3/600, start distance 6, start pitch 18°).

### Materials
Nearly everything uses runtime-created `Material(Shader.Find("Universal Render Pipeline/Lit"))` (with a `?? Shader.Find("Standard")` fallback) rather than `.mat` asset files — colors are set directly in code (e.g. asphalt `(0.24, 0.25, 0.26)`, berm olive `(0.38, 0.44, 0.32)`, safety orange `(1.0, 0.35, 0.0)`). To change a color, find the relevant `Color(...)` literal and edit it in place.

## J. Common Failure Modes + Exact Fixes

1. **Hand-edited scene changes disappear.** Cause: someone ran `Build Aizawl Valley Scene (Dedicated)` (or the Editor auto-build hook fired on a fresh load), which wipes and regenerates the whole scene. Fix: make the change in `AizawlValleySceneBuilder.cs` instead (Section G).

2. **Player gets stuck / hard-stops partway up a ramp, or gets knocked into a non-cardinal rotation near a building.** This was the dominant bug class this session. Root causes found and fixed, in order of discovery: (a) non-convex `MeshCollider`s on the visual ramp meshes — Unity's `CharacterController` cannot reliably climb a non-convex mesh collider; fix was `StripColliders(ramp)` and rely purely on the invisible `SlopedRouteRamp` `BoxCollider`. (b) The invisible ramp box's `run` parameter not matching the visual ramp's actual `localScale.z` footprint (was mismatched by 2x+) — fix was setting `run` to match the visual mesh scale exactly. (c) The invisible ramp box being too thin (`0.9`) causing "skin width" fall-through jitter — fixed by increasing height to `1.6`. (d) An overlapping flush road-strip collider sitting slightly above/astride the start of a ramp collider at the same seam — fixed by `StripColliders` on the last couple of redundant road tiles right before a ramp begins. (e) A large rotated building's generic 4x4x4 collider reaching far enough into the walkway to physically shove the player (visible as the player's `Rotation.Y` getting knocked to a non-cardinal value, e.g. 177.4°, under continuous forward input — that specific symptom is the tell for "something just hit the player," not an input problem) — fixed by moving `House_L2_West/East` from `X=±12` to `X=±17`. **If a similar stuck point appears again: check for (a) non-convex mesh colliders on anything meant to be walked on, (b) mismatched invisible-ramp-box `run` vs. the visual mesh's real footprint, (c) overlapping colliders at a seam between two systems (road + ramp, ground + berm), (d) a nearby large rotated object's generic collider intruding on the path.** Live-test by holding W and watching the Player's Transform Position/Rotation in the Inspector — a fixed position under continued input is a real block; a non-cardinal Rotation.Y after a collision is evidence of a physical shove, not an input/focus issue.

3. **RESOLVED (verified in a later session).** The Level 2 -> Level 3 approach (around Z≈37-38) previously had an unresolved/unverified fix. The `House_L2_West/East` widening to `X=±17` (see #2e above) is confirmed still present in `AizawlValleySceneBuilder.cs` (grepped directly in the source) and has been baked into the active scene across multiple rebuilds performed since, including the autonomous polish pass. If a similar stuck point ever reappears near this zone, re-apply the diagnostic method from #2 above (check Position/Rotation for a physical-shove signature vs. a hard stop) rather than guessing.

4. **RESOLVED (autonomous polish pass).** The Terrain Info panel used to show nothing / never update in the Aizawl Valley scene, because `TerrainService.Active` is always `null` here (no `ITerrainDataProvider` is ever registered in this scene's build path -- that only happens in `DisasterReadyDemo.unity`). Rather than edit the shared `UIBuilder.cs` (which the other scene still needs working), `AizawlValleySceneBuilder.IntegrateGameplay` now disables and hides the panel immediately after `UIBuilder.Build()` returns (`uiResult.TerrainInfo.enabled = false` + `SetActive(false)` on its parent), right in the builder, so the fix re-applies on every rebuild and is never silently lost. Verified live in Play Mode: the panel no longer appears; the rest of the HUD (mission/XP panel, "OFFLINE READY" panel) is untouched.

5. **Git commands hang or fail with `index.lock`/`HEAD.lock: File exists` on this machine's connected-folder mount.** The mount rejects plain `unlink()` on files inside `.git` (git's own temp/lock cleanup step) with "Operation not permitted," even though `rename()`/`mv` works fine. Symptom: a `git add`/`git commit` either hangs for 1-2 minutes (git internally retrying to remove a leftover lock) or fails immediately with "Another git process seems to be running... remove the file manually to continue," even though nothing else is actually touching the repo. **Fix used this session:** `mv .git/index.lock somewhere_outside_.git` (or `.git/HEAD.lock` for the ref-lock variant) immediately before retrying the git command — `mv` succeeds where `rm`/git's internal unlink does not. A one-off `_to_delete/` folder in the repo root (untracked, never `git add`ed) was used as the destination. If this keeps happening, the durable fix is to have someone grant delete permission on this connected folder (there's a dedicated tool for this on the Claude/agent side; a human working directly at the machine wouldn't hit this at all — it's specific to the sandboxed automation environment, not a property of the repo itself).

6. **CS0618 obsolete-API warnings in `DisasterReadyTransplanter.cs`** (`FindObjectsByType`/`FindObjectsSortMode`). Cosmetic, not a blocker — 4 warnings, 0 errors, present at the start and end of this session, unrelated to any gameplay/environment work done. Fix only if you're already touching that file: use the modern `FindObjectsByType<T>(FindObjectsSortMode.None)` overload per Unity's own warning text.

7. **The Animator controller (`KayKitPlayerAnimator.controller`) shows as modified in git even when you didn't touch animation.** Confirmed this session: Unity re-serializes this asset's internal object `fileID`s (not any actual data/behavior change) whenever it gets re-saved as part of a scene rebuild that touches the player's Animator. The diff is 100% cosmetic (same state machine, same blend tree, only internal reference IDs renumbered) — safe to commit as-is; not a sign of data loss or corruption.

8. **Porcelain `git status`/`git commit` can hang for minutes or exceed a tool timeout entirely on this connected-folder mount, even for a small change.** Root cause: both commands perform an implicit working-tree stat-refresh across the whole `Assets/` folder (thousands of Synty/KayKit files), and per-file stat latency over this mount is high -- it is NOT related to the size of the file(s) actually being committed (a 1.6-2MB `.unity` scene blob writes via `git hash-object -w` in ~0.1s; `git write-tree` completes in a few seconds; the working-tree scan is the sole bottleneck). **Fix: bypass the working-tree scan by committing via plumbing instead of porcelain:**
   1. Stage the changed file(s): `git update-index --cacheinfo 100644,<blob-sha>,<path>` (get `<blob-sha>` from `git hash-object -w <path>`), or plain `git add <path>` for small files.
   2. `git write-tree` -> prints a tree SHA.
   3. `git commit-tree <tree-sha> -p <parent-commit-sha> -F <path-to-a-message-file>` -> prints a new commit SHA.
   4. `git update-ref refs/heads/main <new-commit-sha>` -> moves the branch pointer, no working-tree touch.
   This full sequence typically completes in 1-5 seconds total versus 175s+ timeouts for the equivalent porcelain `git commit` on this mount. Combine with the item 5 lock-file workaround above (`mv` any stale `.git/index.lock`/`.git/HEAD.lock` into `_to_delete/` before each step). After a plumbing commit, verify with `git log --oneline -3` or `cat .git/refs/heads/main` rather than `git status` (also slow) -- both are fast, read-only, and don't touch the working tree.

## K. Git Workflow

- Remote: `origin` = `https://github.com/kvritesh/DisasterReady-UnitySimulator.git`. Single branch, `main`.
- **Never force-push, never `reset --hard`, never squash/delete existing commits or tags** — this repo's checkpoint commits are the project's real backup history; there is no other backup.
- `.gitignore` already correctly excludes `Library/`, `Temp/`, `Obj/`, `Build*/`, `Logs/`, `UserSettings/`, and IDE files — do not `git add` those, and do not `git add -A`/`git add .` (there is a stray untracked `_to_delete/` folder full of leftover lock-file debris from this session's git workaround — it must never be committed; delete it by hand once you've confirmed nothing in it matters, or just leave it untracked indefinitely).
- Normal workflow: `git add <specific files>` (name them explicitly), `git commit -m "..."`, `git push origin main`. If a command hangs or fails with a `.lock` error, see Section J item 5.
- To find prior checkpoints: `git log --oneline --decorate -30`. Tag `v0.7.1` marks the very first baseline commit (`c20e47e`).
